# Локальная проверка Telegram manager notifications

## Настройки

В `.env.local` нужны существующие переменные:

```dotenv
TELEGRAM_MANAGER_NOTIFICATIONS_ENABLED=true
TELEGRAM_BOT_TOKEN=<токен бота>
TELEGRAM_MANAGER_INVITE_CODE=<секретный код приглашения>
TELEGRAM_WEBHOOK_SECRET=<отдельный секрет webhook>
TELEGRAM_WEBHOOK_URL=https://<публичный-домен>/api/telegram/webhook
DATABASE_URL=file:./data/local.db
```

Укажите **существующий DATABASE_URL**, не меняя рабочую базу. Все процессы запускайте из корня репозитория с одной `.env.local`. Invite code и webhook secret: 16–128 символов `A-Z a-z 0-9 _ -`, разные значения. Для Avito E2E остаются существующие `AVITO_CHANNEL_ENABLED=true`, `AVITO_CLIENT_ID`, `AVITO_CLIENT_SECRET`, `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL`. Новых env нет.

Бот проекта: `@AvitoAgent2501_bot`. Актуальное состояние настроек и число менеджеров проверяет `npm run smoke:telegram`. Секреты в логи не выводятся.

Локальная настройка 15.09.2026: Telegram включён, секрет создан и webhook зарегистрирован. Next.js работает на порту 3001. Cloudflare-туннель направлен на локальный relay `127.0.0.1:3101`, который пропускает только POST `/api/telegram/webhook`; остальные пути возвращают 404. Локальные вспомогательные файлы и логи находятся в `%LOCALAPPDATA%\avito-partner-ai\telegram-local`. Очередь уведомлений запущена отдельным фоновым процессом. Эта настройка действует, пока работают компьютер, приложение, relay, туннель и очередь; после перезапуска туннеля требуется записать его новый адрес и повторно выполнить `npm run configure:telegram-webhook`.

## Процессы и регистрация

1. Примените существующие миграции с загрузкой той же `.env.local`: `node --env-file-if-exists=.env.local node_modules/drizzle-kit/bin.cjs migrate`.
2. Терминал 1: `npm run dev -- --port 3001`.
3. Обеспечьте публичный HTTPS-туннель к `http://localhost:3001`. Например, при установленном cloudflared: `cloudflared tunnel --url http://localhost:3001`. Оставьте процесс туннеля работающим. Скопируйте выданный HTTPS-домен в `TELEGRAM_WEBHOOK_URL`, добавив `/api/telegram/webhook`. При смене адреса туннеля повторите настройку webhook. [Telegram требует HTTPS для setWebhook](https://core.telegram.org/bots/api#setwebhook).
4. После заполнения env перезапустите сервер. Выполните `npm run configure:telegram-webhook`; ожидается `TELEGRAM_WEBHOOK=PASS configured=true`.
5. Откройте личный чат с `@AvitoAgent2501_bot`, отправьте `/start`, затем **отдельным сообщением** значение `TELEGRAM_MANAGER_INVITE_CODE`. Бот должен подтвердить включение уведомлений. Передавайте код только менеджерам.
6. Отправьте `/status`: ответ «Уведомления … включены» и `Chat ID: <число>`. Это ID для адресного smoke. Каждый дополнительный менеджер регистрируется так же **до handoff тестового лида**. `/stop` отключает его; повторный ввод кода включает только будущие уведомления.
7. Диагностика без отправок: `npm run smoke:telegram`. Проверьте `enabled=true`, `webhookConfigured=true`, `activeManagers>=1`.
8. Адресная реальная проверка (подставьте **свой тестовый** Chat ID):

   ```powershell
   npm run smoke:telegram -- --chat-id <TEST_MANAGER_CHAT_ID> --send
   ```

   Сообщение «🧪 Тест уведомлений менеджера» получит только этот активный зарегистрированный менеджер. Лид и production-уведомление не создаются. В консоли: `status=SENT`, `providerMessageId`, `latencyMs`. Каждый явный запуск `--send` отправляет отдельный технический тест; проверка handoff-dedup выполняется ниже.

## Реальный Avito → handoff → Telegram

1. Зарегистрируйте всех тестовых менеджеров. Выберите контролируемый Avito-чат **без прежнего handoff**. Повторно использовать уже переданного лида для проверки новой карточки нельзя: dedup должен запретить повтор.
2. Терминал 2 — только выбранный тестовый Avito-чат:

   ```powershell
   npm run poll:avito -- --continuous --interval-ms 10000 --chat-id <TEST_AVITO_CHAT_ID>
   ```

3. Терминал 3 — существующая очередь доставки и retry:

   ```powershell
   npm run notify:telegram -- --continuous --interval-ms 10000
   ```

   Первичная отправка уже вызывается workflow сразу после handoff. Этот процесс доставляет оставшуюся очередь и повторяет только неуспешные доставки по существующим ограничениям (до трёх попыток). Он не меняет Avito polling и не вызывает Claude. Очередь общая: процесс обслуживает все допустимые реальные handoff, а не только выбранный Avito-чат.
4. С клиентского аккаунта проведите тестовый диалог: город Химки, капитал 150 000 ₽, запуск одного объекта в течение месяца, цель — свой бизнес/дополнительный доход, принятие модели и готовность финансировать аренду, залог, оснащение и взаимодействовать с управляющей компанией. Отвечайте на реальные уточнения бота. Не выдавайте тестовые сведения за данные случайного клиента.
5. До телефона карточки быть не должно. После запроса телефона отправьте свой действительный номер. В CRM проверьте сохранённый телефон, сегмент, квалификацию, handoff и статус Telegram. Откройте Telegram у каждого зарегистрированного менеджера: должна быть одна карточка «🔥 Новый квалифицированный лид» с этим телефоном и ID Avito-чата.
6. Подождите минимум три цикла polling и очереди, затем перезапустите polling с той же командой. Новых карточек этого лида быть не должно. Сообщение «Спасибо» после handoff также не создаёт новую карточку. Входящий event и handoff имеют прежние ключи dedup; в SQLite `telegram_manager_deliveries` — одна запись на сочетание уведомления и менеджера, `external_message_id` соответствует полученной карточке.
7. Для проверки `/stop` отключите одного менеджера и проведите **другого** тестового лида. Для проверки отсутствия рассылки задним числом зарегистрируйте нового менеджера после handoff: старую карточку он не получает.

## Диагностика доставки

В workflow ищите `manager_notification.sent` / `manager_notification.failed`; в очереди дополнительно `telegram_manager_delivery.sent` / `.failed`, `recipientId`, `notificationId`, `providerMessageId`, `latencyMs`. В SQLite таблица `telegram_manager_deliveries` содержит отдельные статусы, число попыток и Telegram message ID каждого получателя. Ошибка одного менеджера не откатывает handoff и не повторяет успешные доставки другим.

`TELEGRAM_NO_ACTIVE_RECIPIENTS`: на момент handoff не было подходящих зарегистрированных менеджеров; старые карточки не будут рассылаться новым менеджерам. `TELEGRAM_HANDOFF_NOT_ELIGIBLE`: нет финального handoff/подтверждённого валидного телефона или сохранён NO_FIT. Эти записи завершаются без сетевой отправки и не занимают очередь бесконечно. Исторические некорректные handoff автоматически не переотправляются.

HTTP 401/403 — проверить токен/доступ к чату; 429/5xx и сетевые сбои используют существующий retry. При неоднозначном сетевом обрыве после приёма сообщения Telegram абсолютный exactly-once не гарантируется: `sendMessage` не имеет idempotency key; локальный dedup защищает подтверждённые доставки и повторный polling. Проверки кода используют изолированную SQLite и подмену только внешних сервисов, без рассылки живым менеджерам.

## Переезд в production

1. Подготовьте постоянный HTTPS-домен и endpoint `/api/telegram/webhook` на production-сервере. Локальный туннель больше не нужен.
2. Перенесите текущие секреты через настройки окружения сервера. Токен бота, invite code и webhook secret можно сохранить. Установите `TELEGRAM_WEBHOOK_URL=https://<production-домен>/api/telegram/webhook`.
3. Остановите локальные процессы polling/очереди и приём webhook перед финальным переносом базы. Сделайте согласованную резервную копию SQLite при остановленных процессах приложения. Перенесите всю базу, включая менеджеров, Telegram deliveries и ключи dedup, на постоянный диск production-сервера; укажите её новый путь в `DATABASE_URL`. Не запускайте локальную и production-копии очереди одновременно с разошедшимися базами.
4. Запустите production-приложение и выполните `npm run configure:telegram-webhook` в production-окружении. Telegram переключит единственный webhook этого бота на новый URL. Команда не удаляет ожидающие обновления.
5. Запустите polling и `npm run notify:telegram -- --continuous --interval-ms 10000` под супервизором процессов. Проверьте `/status` и адресный smoke. Менеджерам не нужна повторная регистрация, если сохранены тот же бот и база.
