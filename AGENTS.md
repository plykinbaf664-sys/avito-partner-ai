# AGENTS.md

# AI Partner Qualification System
## Engineering & Agent Operating Instructions

Этот файл — главный набор правил для AI-агентов, работающих с репозиторием.

Он определяет:
- что мы строим;
- зачем мы это строим;
- как принимать архитектурные решения;
- где допустима автономность;
- где нужны строгие правила;
- как проверять качество;
- когда задача считается завершённой.

Если локальная техническая реализация противоречит этому документу,
приоритет имеет этот документ и бизнес-цель проекта.

---

# 1. Миссия проекта

Мы создаём AI-систему первичной обработки и квалификации входящих партнёров для бизнеса посуточной аренды.

Это НЕ:
- обычный чат-бот;
- FAQ;
- форма-анкетирование;
- генератор ответов;
- CRM ради CRM;
- демонстрационный AI-прототип.

Это бизнес-система, задача которой:

входящий лид
→ диалог
→ понимание ситуации
→ выявление цели и барьеров
→ сбор квалификационных данных
→ ответы на разрешённые вопросы
→ классификация
→ подготовка контекста
→ передача подходящего лида менеджеру.

Система должна уменьшать объём ручной первичной работы менеджеров без потери потенциально ценных партнёров.

---

# 2. Бизнес-контекст

Пользователь приходит с интересом к запуску бизнеса на посуточной аренде.

Компания помогает партнёру:
- искать объекты;
- договариваться с собственниками;
- запускать объекты;
- размещать объявления;
- управлять бронированиями;
- организовывать клининг;
- настраивать дистанционное заселение;
- координировать горничных;
- работать с гостями;
- управлять календарями;
- использовать CRM;
- после запуска взаимодействовать с персональным менеджером.

Партнёр является владельцем собственного бизнеса и несёт расходы по нему.

Компания выступает как управляющая сторона.

---

# 3. Текущие квалификационные данные

Минимальный бюджет:
150 000 ₽.

Приоритет:
партнёр, способный потенциально запустить 5 объектов.

5 объектов являются приоритетным профилем,
но НЕ автоматически обязательным условием для всех лидов.

Приоритетные города:

- Видное
- Подольск
- Домодедово
- Балашиха
- Химки
- Волгоград

Стартовая финансовая модель:

- поиск объекта — 100% от стоимости объекта согласно текущей бизнес-формулировке;
- размещение объекта на одной площадке — 500 ₽;
- обработанная и заселённая бронь — 100 ₽ / сутки.

Не интерпретировать неоднозначные бизнес-формулировки самостоятельно.

Если бизнес-значение параметра неизвестно —
вынести его в конфигурацию / TODO / вопрос владельцу проекта.

---

# 4. Доходность

Внутренний ориентир бизнеса:

- около 30 000 ₽ на один объект;
- около 150 000 ₽ на пять объектов.

Это НЕ гарантия.

AI запрещено:
- гарантировать доход;
- гарантировать окупаемость;
- обещать конкретную прибыль;
- придумывать цифры;
- представлять ориентир как гарантированный результат.

Допустимо объяснять:

"По действующим объектам компании есть такой ориентир, но экономика зависит от города, объекта, загрузки и расходов. Перед запуском необходимо считать конкретный объект."

# 5. Главная продуктовая идея

Квалификация — это не анкета.

Плохой workflow:

город
→ бюджет
→ время
→ срок
→ менеджер.

Хороший workflow:

понять ситуацию
→ определить мотив
→ понять главный барьер
→ дать релевантный ответ
→ естественно собрать данные
→ определить готовность
→ передать менеджеру контекст.

Система должна делать часть интеллектуальной работы менеджера до handoff.

---

# 6. Какого "сотрудника" мы создаём

Перед изменением поведения системы воспринимай AI как сотрудника компании.

Его роль:

AI-квалификатор входящих партнёров.

Его цель:

помочь подходящему человеку понять предложение,
собрать необходимый контекст,
не потерять потенциально ценного лида
и передать менеджеру подготовленного кандидата.

У него есть:

## Руки / tools

- получение входящего сообщения;
- отправка ответа;
- чтение и запись профиля лида;
- чтение истории диалога;
- чтение базы знаний;
- изменение conversation state;
- запуск qualification rules;
- создание handoff;
- уведомление менеджера.

## Знания

Только утверждённая Knowledge Base.

## Память

- профиль лида;
- история сообщений;
- извлечённые факты;
- текущий state;
- выявленные вопросы;
- выявленные барьеры;
- ранее отправленная информация.

## Что он решает самостоятельно

- как естественно сформулировать ответ;
- какой разрешённый вопрос задать следующим;
- какую релевантную информацию из Knowledge Base использовать;
- какое намерение содержится в сообщении;
- какие факты можно извлечь из текста.

## Что он НЕ решает самостоятельно

- минимальный бюджет;
- бизнес-условия;
- цены;
- юридические обещания;
- финансовые гарантии;
- qualification rules;
- правила handoff;
- разрешённые города;
- условия продукта.

Эти вещи задаются детерминированно.

# 7. Главное архитектурное правило

Максимум свободы там,
где нужна интеллектуальная адаптация.

Максимум жёсткости там,
где ошибка дорогая.

Поэтому:

LLM может свободно:
- понимать язык;
- определять intent;
- адаптировать формулировку;
- выбирать естественный переход;
- суммировать разговор.

LLM не может свободно:
- изменять цены;
- менять qualification thresholds;
- обещать доход;
- самостоятельно решать бизнес-правила;
- изменять права доступа;
- удалять критичные данные;
- инициировать опасные внешние действия.

---

# 8. Agentic ≠ Automation

Перед созданием нового AI-agent определить:

нужен ли вообще AI для этой задачи?

Если маршрут всегда:

A → B → C

и не зависит от контекста,
использовать обычную программную логику.

AI нужен там, где следующий шаг зависит от:
- смысла сообщения;
- текущей ситуации;
- истории разговора;
- намерения пользователя;
- сочетания нескольких факторов.

Примеры automation:

budget >= MIN_BUDGET
→ budgetQualified = true

duplicate external_event_id
→ reject duplicate

status = HOT
→ create handoff

Примеры agentic behavior:

пользователь не ответил на вопрос,
а задал другой вопрос
→ понять вопрос
→ ответить
→ определить, стоит ли возвращаться к предыдущему вопросу.

Не превращать детерминированную бизнес-логику в AI.

# 10. Текущая база данных

На локальной стадии:

SQLite.

SQLite — реализация хранения,
но НЕ часть domain logic.

Не писать бизнес-логику напрямую против SQLite.

# 12. Conversation state

Диалог должен иметь сохраняемое состояние.

Минимальный набор:

NEW

DISCOVERY

QUALIFYING

WAITING_CITY

WAITING_GOAL

WAITING_EXPERIENCE

WAITING_BARRIER

WAITING_BUDGET

WAITING_TIME

WAITING_LAUNCH_TIMING

QUALIFIED

HANDOFF

CLOSED

State — это контекст, а не жёсткая анкета.

Пользователь может сообщить несколько фактов одновременно.

Если пользователь написал:

"Я из Волгограда, есть 500 тысяч, хочу начать через месяц"

нельзя потом спрашивать:
- город;
- бюджет;
- срок запуска.

# 13. Qualification statuses

Поддерживать:

NEW

QUALIFYING

PRIORITY

HOT

WARM

NURTURE

NO_FIT

HANDOFF

CLOSED

Business Rules Layer принимает итоговое решение.

LLM может предоставлять структурированные факты,
но не является единственным источником qualification status.

---

# 14. Structured Extraction

LLM должен преобразовывать неструктурированный текст в typed output.

Например:

{
  "intent": "QUALIFICATION_ANSWER",
  "facts": {
    "city": "Волгоград",
    "budget": 500000,
    "launchTiming": "WITHIN_MONTH"
  },
  "questions": [],
  "objections": [],
  "possiblePrimaryFear": "FEAR_LOW_DEMAND"
}

Любой output LLM:

- валидировать через Zod;
- считать недоверенным внешним вводом;
- не записывать в domain без validation.

---

# 15. Business Rules

Все дорогие решения реализовывать обычным TypeScript.

Пример:

MIN_PARTNER_BUDGET = 150_000

Если budget < MIN_PARTNER_BUDGET:
не считать финансовую квалификацию пройденной.

Приоритетный кандидат:

имеет достаточный бюджет / намерение
для масштабирования примерно до 5 объектов
и демонстрирует реальную готовность к запуску.

Не делать:

LLM → "мне кажется, это PRIORITY".

Делать:

facts
→ deterministic rules
→ status.

# 17. Prompt philosophy

Prompt должен описывать:

- цель;
- контекст;
- доступные tools;
- ограничения;
- критерии успешного результата;
- критерии завершения.

Не микроменеджить каждый шаг модели,
если задача требует интеллектуальной адаптации.

Современной модели чаще полезнее дать:

goal
+ context
+ tools
+ rules
+ done criteria

и позволить ей самой выбрать разумный путь.

Исключение:

если цена ошибки высокая,
путь должен ограничиваться программно.

# 18. Before coding

Перед существенной реализацией агент должен сначала ответить:

1. Какую проблему он решает?
2. Как выглядит хороший результат?
3. Какие компоненты затронуты?
4. Какие данные изменяются?
5. Какие внешние зависимости есть?
6. Где требуется AI?
7. Где AI не нужен?
8. Какие ошибки наиболее дорогие?
9. Как это будет протестировано?
10. Как проверить результат end-to-end?

Только после этого переходить к реализации.

# 19. Определение хорошего результата

Перед реализацией каждой значимой функции определить измеримые критерии.

Рассматривать как минимум:

## Accuracy

Насколько правильно:
- извлекаются факты;
- определяется intent;
- применяется qualification rule;
- формируется handoff.

## Task success

Выполнил ли workflow бизнес-задачу полностью?

Например:

сообщение
→ обработка
→ сохранение
→ qualification
→ handoff.

## Cost

Сколько:
- LLM calls;
- tokens;
- внешних API requests

требуется на один workflow.

Не оптимизировать стоимость раньше надёжности,
но не создавать бессмысленные AI-вызовы.

## Latency

Измерять время:
- webhook acceptance;
- AI processing;
- full response;
- handoff.

## Human intervention rate

Какой процент диалогов требует человека?

Сам по себе высокий или низкий показатель не является плохим.

Важно понимать причины вмешательства.

## Error rate

Отдельно отслеживать:

false HOT

false NO_FIT

missed handoff

duplicate processing

hallucinated business fact

lost message.

Не придумывать целевые проценты без данных.

До появления реального baseline:
метрики собираются,
а acceptance threshold определяется отдельно для каждой критичной функции.

# 20. Самые дорогие ошибки

Считать критическими:

1. Потерянное входящее сообщение.
2. Потерянный потенциальный партнёр.
3. Неверный NO_FIT.
4. Повторная отправка пользователю.
5. Повторный handoff.
6. Выдуманная информация о продукте.
7. Выдуманная доходность.
8. Неверная цена.
9. Утечка секретов.
10. Повреждение/удаление данных.

Архитектура должна быть особенно жёсткой вокруг этих сценариев.

---

# 21. Idempotency

Любой внешний event потенциально может прийти повторно.

Каждое входящее событие должно иметь:

source
externalEventId

Повторное событие не должно:

- создавать второго лида;
- повторно сохранять одно сообщение;
- повторно вызывать LLM;
- повторно отправлять ответ;
- повторно создавать handoff.

---

# 22. Error handling

Ошибки внешних сервисов не должны приводить к потере данных.

Persist first.

Then process.

Если LLM недоступен:

- сохранить событие;
- сохранить сообщение;
- зафиксировать ошибку;
- разрешить retry.

Разделять:

retryable errors

non-retryable errors.

---

# 23. Observability

Система должна позволять восстановить цепочку:

что пришло
→ что сохранилось
→ что понял AI
→ какие facts извлечены
→ какое правило сработало
→ какой state изменился
→ какой ответ сформирован
→ был ли handoff.

Использовать structured logging.

Основные identifiers:

requestId
eventId
leadId
conversationId
source.

# 24. Security

Никогда не коммитить:

- API keys;
- tokens;
- passwords;
- secrets;
- production credentials.

Использовать:

.env.local

и

.env.example

В `.env.example` только названия переменных без секретных значений.

Не логировать секреты.

Минимизировать передачу персональных данных LLM.

# 25. Testing philosophy

Тестировать не только функции.

Тестировать поведение бизнеса.

Нужны:

unit tests

integration tests

workflow tests.

Unit test отвечает:

"правильно ли работает функция?"

Workflow test отвечает:

"получил ли бизнес нужный результат?"

---

# 26. Тестировать весь workflow

Tool A может работать идеально.

Tool B может работать идеально.

Tool C может работать идеально.

Но:

A → B → C → D

может не работать вообще.

Поэтому критические сценарии обязательно проверять end-to-end или workflow-level тестами.

Пример:

incoming message
→ persistence
→ extraction
→ state update
→ qualification
→ response
→ handoff.

Если каждый модуль зелёный,
но workflow не завершён —
задача НЕ считается выполненной.

---

# 27. Не микроменеджить модель

Prompt должен описывать:

- цель;
- контекст;
- tools;
- правила;
- ограничения;
- критерий завершения.

Не задавать огромный сценарий:

"сначала сделай X,
потом ровно Y,
затем ровно Z"

там, где последовательность должна зависеть от пользователя.

Давать свободу интеллектуальной адаптации.

---

# 28. Свобода против жёсткости

Главное правило проекта:

МАКСИМУМ СВОБОДЫ
там, где нужно понять человека.

МАКСИМУМ ЖЁСТКОСТИ
там, где ошибка стоит денег, лида или доверия.

Использовать AI для:

понимания.

Использовать код для:

контроля.

---

# 29. Agentic vs Automation

Перед созданием агента спросить:

"Нужно ли здесь выбирать следующий шаг?"

Если нет:

не нужен agent.

Использовать workflow / function / rules.

Agent нужен только когда:

контекст влияет на маршрут.

Не использовать AI ради слова AI.

---

# 30. Перед vibe-coding представить систему как компанию

Перед созданием любой agentic subsystem ответить:

Кто сотрудник?

Какова его цель?

Какие у него инструменты?

Какими знаниями он располагает?

Что он помнит?

Какие решения принимает самостоятельно?

Когда обращается к руководителю / человеку?

Какие ошибки ему запрещены?

Как измеряется качество его работы?

Что означает "работа завершена"?

Если на эти вопросы нет ответа —
не начинать реализацию agentic behavior.

---

# 31. Не создавать технический долг ради скорости

MVP означает:

минимальный объём продукта.

MVP НЕ означает:

грязная архитектура.

Допустимо:
- меньше функций;
- меньше интеграций;
- простая UI;
- локальная база.

Недопустимо:
- смешивать domain и integrations;
- хардкодить бизнес-правила в prompts;
- хранить состояние только в памяти;
- разбрасывать magic numbers;
- обходить типизацию;
- отключать тесты;
- коммитить secrets.

Лучше реализовать меньше,
но правильно.

# 33. Изменения

Перед изменением существующего поведения:

1. Изучи текущую реализацию.
2. Найди связанные тесты.
3. Определи бизнес-инварианты.
4. Сохрани обратную совместимость, если нет причины её ломать.
5. Добавь/измени тест.
6. Реализуй минимально необходимое изменение.
7. Запусти весь релевантный workflow.

Не переписывать рабочие подсистемы без необходимости.

---

# 34. Работа с неизвестностью

Если что-то неизвестно:

не придумывать.

Разделять:

BLOCKING UNKNOWN

и

NON-BLOCKING UNKNOWN.

Если блокирует корректную реализацию:
спросить владельца проекта.

Если не блокирует:
выбрать минимальное обратимое решение,
явно зафиксировать assumption
и продолжить.

---

# 35. Human handoff

AI обязан передать человеку управление, если:

- пользователь прямо просит человека;
- пользователь хочет созвон;
- хочет оплатить;
- хочет обсуждать договор;
- хочет считать конкретный объект;
- вопрос находится вне Knowledge Base;
- возникает высокая неопределённость;
- действие может иметь финансовые/юридические последствия;
- AI не уверен, что имеет право отвечать.

# 37. Definition of Done для кода

Работа не завершена только потому,
что агент написал код.

pnpm lint

# 38. Definition of Done для поведения

Для agentic-функции дополнительно проверить:

- happy path;
- partial information;
- пользователь ответил сразу на несколько вопросов;
- пользователь изменил предыдущий ответ;
- пользователь задал вопрос вместо ответа;
- unknown question;
- human handoff;
- duplicate input;
- external API failure;
- return after pause.

# 39. Definition of Done для workflow

После изменения ответить:

1. Какой пользовательский workflow проверен?
2. Какой результат ожидался?
3. Что произошло фактически?
4. Какие метрики доступны?
5. Где остался риск?
6. Требуется ли вмешательство человека?

Без workflow verification
критичная задача не считается законченной.

# 40. Работа агента в репозитории

Перед началом задачи:

1. Прочитать AGENTS.md.
2. Изучить релевантные файлы.
3. Проверить текущую архитектуру.
4. Не предполагать наличие модулей, которых нет.
5. Сформировать короткий plan.
6. Реализовать.
7. Проверить.
8. Сообщить результат.

Не спрашивать подтверждение на каждое безопасное техническое действие.

Но не принимать самостоятельно необратимые бизнес-решения.

Коротко.

Только существенные.

- workflow tests
- build

Без сокрытия проблем.

Конкретные TODO.

Один наиболее логичный этап.

# 42. Ultimate principle

Код не является целью.

Цель:

надёжное бизнес-поведение системы.

Перед каждым техническим решением задавай вопрос:

"Увеличивает ли это вероятность того,
что система правильно поймёт входящего человека,
не потеряет его,
корректно квалифицирует
и вовремя передаст менеджеру?"

Если нет —
скорее всего, это не приоритет.
